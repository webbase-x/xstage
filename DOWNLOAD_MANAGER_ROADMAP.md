# X-Stage Download Manager — Implementation and Release Gates

Scope: Enhance the **existing** `download-manager/` application in `webbase-x/xstage`. Never replace it with a new unrelated product. The public download remains **one Windows x64 Setup EXE**. The installer may remain unsigned until an independently verified code-signing certificate is provisioned. Never claim an EXE is released until GitHub Actions, GitHub Release asset and public SHA-256 feed all agree.

## Master target — Download & Media Acquisition Engine

The long-term target is an IDM / aria2 / yt-dlp / JDownloader-class application while keeping the existing X-Stage product and data model. Build it as a durable engine first, then layer UI and automation on top.

- **Core transfer engine:** HTTP/HTTPS multi-connection Range downloads (1/2/4/8/16/32), single-stream fallback, transactional per-chunk resume, bounded retry/backoff, queue priorities, global/per-job bandwidth limits and adaptive concurrency.
- **Authenticated/request-aware HTTP:** explicit custom headers, Cookie, User-Agent, Referer and optional HTTP/SOCKS5 proxy support. Never silently bypass access controls; expired/session-bound URLs must be refreshed by an authorized extractor/session flow or reported clearly.
- **Modern media acquisition:** HLS `.m3u8`, DASH `.mpd`, quality/bitrate selection, concurrent segments, multi-audio, subtitles, metadata/cover where authorized, yt-dlp extractor integration, FFmpeg/FFprobe mux/remux/transcode and resumable media fragments. No DRM bypass.
- **Integrity and filesystem safety:** user-supplied SHA-256 with SHA-1/MD5 only for compatibility, disk preflight/low-disk pause, temporary/partial files, atomic finalization, filename sanitization, collision policy (rename/skip/overwrite/ask), stable server identity and byte/media verification before Completed.
- **Organization and automation:** multiple named queues, start/stop schedules, smart destination rules by extension/domain/size/pattern, batch URL/text import and numeric expansion, filtered clipboard capture, browser handoff with user-approved session data, and explicit post-download actions. Never execute downloaded content or arbitrary shell commands without clear user approval.
- **Power-user operation:** per-chunk telemetry, smoothed speed/ETA, structured per-job logs with token redaction, crash diagnostics, high-DPI/accessibility, engine/UI separation, optional CLI/headless/local API and future Web UI without exposing an unauthenticated public service.
- **Optional protocols last:** FTP/SFTP and BitTorrent/Magnet only after security/privacy/licensing review; never let optional protocols destabilize the HTTP/media core.

## Gate for every milestone

1. Preserve installed users' data, existing output media and prior working capabilities.
2. Compile and run deterministic .NET integration tests on GitHub Actions Windows runner, including failure/recovery cases.
3. Validate real downloaded bytes for HTTP, full media streams using FFprobe/FFmpeg, and verified SHA-256 for update binaries. Do not mark partial media Completed.
4. Package verified self-contained Windows EXE; require successful GitHub Release asset publication and matching public update manifest.
5. Clearly distinguish CI verification from real-device field testing. If field testing is absent, state that explicitly.
6. Progress is visible; no silent indefinite waits, hidden failures, automatic execution of downloaded files or bypassing protected media.

## Durable engineering rules

- Treat the physical `.part` byte count as the authority for resume; never append a mismatched HTTP 206/200 response or merge fragments with different validators.
- SQLite checkpoints must be transactional. Never delete the original legacy JSON or an existing completed file as part of migration/retry.
- Limit site rate/fragment concurrency and honor retry windows. Reject unsafe, expired or unauthorized media URLs instead of bypassing authentication.
- UI sorting and filtering must not mutate the queue, overwrite files or cause actions on the wrong job.
- Release every milestone independently with tests and verifiable EXE checksum; proceed to the next implementation only after the preceding gate passes.
